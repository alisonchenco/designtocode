    Design-to-code essentials

    Practical steps for layouts, reusable components,
    and responsive handoffs.

    01Give your layouts a little logic.

    A layout should explain how elements relate, not just where they sit in one screenshot.

    • Use auto layout for rows, stacks, and repeated content. Define padding, gaps, alignment, and wrapping instead of positioning every element manually.
    • Choose fixed, fill, or content-sized dimensions intentionally. Show what grows when text wraps and what stays aligned.
    • Name layers by their role, such as Product card or Primary action, and keep the hierarchy close to the interface's structure.

    Try this: Replace a short heading with a long one. Does the card grow naturally without overlapping its neighbors?

    02Turn repeated decisions into a system.

    Consistency works best when design and code share the same building blocks.

    • Use components for repeated patterns. Define variants for meaningful differences, such as size and state, instead of detaching every instance.
    • Use semantic tokens for colors, type, spacing, and radii. A name like color.text.secondary communicates intent better than a hex value.
    • Agree on component and token names with developers. Check the existing code library before designing a new version of something it already supports.

    Try this: Change your primary color token. Every primary action should update without editing individual screens.

    03Design the in-between, too.

    The happy path is only one part of a working interface. Make the rest explicit.

    • Show narrow and wide layouts, then describe what stacks, wraps, hides, or scrolls between them. Choose breakpoints based on when content stops fitting.
    • Include focus, hover, disabled, loading, empty, error, and success states where relevant. Note keyboard behavior, labels, and accessible contrast.
    • Use realistic content, including long text and missing images. Document interactions, export required assets, and review the built page together.

    Try this: Walk through the interface using only a keyboard. Can you reach every action and always tell where focus is?

    Three levels of a good handoff

    01

    Build with structure, not guesswork.

    Use auto layout to define padding, gaps, and how the card grows. Test long titles before you hand it off.

    02

    Create a language you both speak.

    Name colors, type, and radii with shared tokens. Match each component variant to a prop in code.

    03

    Make the details part of the design.

    Show default, hover, and empty states. Define what changes on a narrow screen so the build is not left to guesswork.

    AI handoff

    Levels 1 to 3 get your file right. Guardrails keep AI-generated code true to it.

    01Why it matters

    AI coding tools copy whatever structure you give them. A messy file gets messy code, faster. Guardrails make the model follow your system instead of improvising.

    02What you own
    • Auto layout and variables in the Figma file.
    • Component variants that match the props in code.
    • Code Connect mappings between Figma components and code.
    • A one-line use when / don't use when note on each component.
    03What to ask engineering for
    • A rules file at the repo root, such as CLAUDE.md or AGENTS.md, or project rules in .cursor/rules.
    • Tokens exported as code, with shared names for colors, spacing, and type.
    • Lint rules that ban hardcoded colors and spacing, with violations failing the build in CI.
    • A Tailwind theme or configuration locked to those tokens.
    04Working with the agent
    1. Work on one frame at a time.
    2. Ask for a plan listing components and gaps before it codes.
    3. Have it screenshot its output and compare it to the Figma frame.
    4. Review every change as a pull request.
    05In code

    Use this sample as a starting point for CLAUDE.md. Adapt the paths and token names to your repository.

    CLAUDE.md
    # UI implementation rules
Use only components from /components/ui.
Use the design tokens exported from tokens.ts.
Never hardcode colors, spacing, or font sizes.
Match component variants to documented props.
If no component fits, stop and ask.
Do not use inline styles.
Do not add dependencies without asking.
Implement one Figma frame at a time.
Before coding, list the components and gaps in a plan.
Screenshot the result and compare it with the Figma frame.
Submit every change for review as a pull request.

    Try this: Give the same Figma frame to an AI tool with and without the rules file. Compare which components and values each version used.
